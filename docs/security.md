# zecsolve development security boundaries

The stateless development POC uses one configured POC bearer token; persisted verification uses separate merchant credentials. Health and OpenAPI routes are public; POC verification requires that token and is disabled when none is configured. Merchant credentials protect owned invoice/case records, encrypted evidence submission/metadata, persisted verification, and initial offline reports. Customer/reviewer access remains unfinished; merchant decisions require authorization and current version checks. Do not expose the POC publicly before the scoped workflow is complete.

Merchant tokens contain 256 random bits, expire after a configured 1–365 days, and are stored only as SHA-256 digests. The operator CLI discloses a token once, only after a successful database commit, and can revoke individual credentials. `/api/auth/me` checks expiry and revocation against the database on every request and returns only the authenticated merchant/credential IDs. The application derives identity from that credential; it does not accept merchant identity from request fields. Customer/reviewer grants and browser login sessions remain pending. Merchant decision endpoints derive authority from the same active credential.

The API limits request bodies to 4,200,000 bytes, receipt files to 16,384 UTF-8 bytes, transaction hex to 4,000,002 bytes, subprocess output to 32,768 bytes, and simultaneous verifiers to two per API process. The default subprocess timeout is ten seconds. Container/process-level memory limits and ingress rate limits remain deployment work.

The adapter invokes a configured local executable with explicit arguments, `shell=False`, no inherited application secrets, no stdin and discarded stderr. It uses a private temporary directory and removes it after processing. No user-specified paths or fetch URLs are accepted. POC evidence is not persisted; the separate merchant evidence workflow stores encrypted bundles. Retention/deletion and multi-key rotation remain separate operational work.

The API returns generic validation errors rather than echoing submitted receipt fields. Access logs are disabled in the documented run commands. Responses use `Cache-Control: no-store`. The returned recovered fields are themselves disclosures and must be handled accordingly.

Only the selected output's amount, recipient and memo are recovered. The receipt's OCK intentionally permits this disclosure; it is not a seed, spending key or wallet-wide viewing key. Anyone who receives a receipt can forward it and verify it again. Removing a reviewer grant later cannot revoke a previously downloaded receipt.

Receipt validity does not establish the sender's identity or intent. An optional valid receipt signature only demonstrates possession of its signing key. Raw transaction recovery does not perform consensus validation or prove chain inclusion. All current verifier reports carry `chain_state=UNAVAILABLE`.

The allocation primary key prevents reuse inside this database. It does not detect reuse in another deployment or prove that the merchant's invoice is truthful. Append-only triggers resist ordinary application edits, not database-administrator tampering. Case event hashes require an implemented writer and a trusted anchor to provide stronger integrity guarantees.

To complete the case workflow: add customer/reviewer grants and consent, validate the trusted RPC adapter against a real node, and implement authorized export. Merchant decision authorization and atomic approval/idempotency are implemented, but deployed offline observations cannot authorize credit. Never infer merchant authority from a valid receipt alone.

Case opening/read is now merchant-scoped. Case creation accepts only an invoice reference and derives actor, ownership, state, version, and audit payload server-side. It commits the case, initial event, and retry result atomically, including concurrent same-invoice and conflicting-key requests. Creation always locks invoice before case and rechecks credential expiry after waiting. GET exposes current case state and the validated opening event; it is not a full evidence report and grants no customer/reviewer access.

Opening-event payloads are limited to the owned invoice ID/hash and policy ID. Events and retry outcomes reject ordinary edits/deletes. Historical hashes are retained without fabricated payloads, and migration rollback locks active writers out before checking whether evidence would be lost. Event hashes are integrity references, not protection against database-administrator tampering.

Recipient normalization is an offline, mainnet-only decoder for a caller-selected Orchard or Sapling receiver. It validates both the outer address and the selected inner receiver, including when the address carries multiple receivers. A valid result establishes a normalized receiver identity; it does not prove that a merchant controls it or that it uniquely identifies an invoice. `unique_receiver_binding` must remain false in the public P0 workflow.

The Python normalizer accepts a validated address request, writes it to a private temporary directory, and uses the same bounded process runner as receipt verification. Address contents are not passed in command-line arguments; no application secrets or stdin are inherited, and stderr is discarded. The result must have schema version 1, bind the request hash, and match its network/pool. Request files are limited to 8,192 bytes and addresses to 1,024 UTF-8 bytes; process output remains capped at 32,768 bytes with the configured timeout. The internal adapter does not provide merchant authorization or an HTTP route. Future workflow routes must authorize callers and apply the shared concurrency limit before invoking it.

Invoice create/read routes now require merchant credentials and apply that shared concurrency limit. The server derives merchant identity, normalizes the receiver, and fixes the policy. Invoice, policy, and scoped retry record commit atomically. Credential expiry/revocation is checked after acquiring its row lock, including reads and replay; normalization holds no database locks. Unavailable database/normalizer errors reveal no internal exception details. Invoice snapshots, policies, and completed retry records reject ordinary updates/deletes; these controls are not protection against a database administrator.

Invoice terms, policy records, evidence metadata, recovered verification fields (including memo and receiver), and evaluation snapshots are not application-encrypted. Keep the hackathon demonstration on public fixtures; deployment encryption/access controls, customer consent, and retention/purge design remain required before real customer use. Creating an invoice neither proves ownership of its receiver nor credits payment. See [invoice API boundaries](invoices.md).

Evidence bundle bodies use AES-256-GCM with a configured external 32-byte secret, fresh 12-byte nonce, full tag, and associated data binding merchant/case/evidence/key/version. Unique key-ID/nonce pairs and immutable ciphertext rows preserve reservations. No public route returns plaintext or ciphertext. Internal decryption verifies authentication and hashes, and reauthorizes the principal before returning content; revocation during decryption prevents that return.

Evidence submission atomically writes ciphertext, immutable metadata and acknowledgement, retry record, case state/version, and a chained audit event. Full history validation precedes appending; encryption holds no database locks and uses the shared capacity limit. Completed retries preserve the original metadata, including after case closure. New uploads to terminal cases are blocked.

`source` and `source_kind`, including `public_fixture`, are unverified labels. Processing acknowledgement records the merchant's assertion, not independent customer consent. Reviewer sharing is forced false. See [evidence setup and disclosure limits](evidence.md) for exact input bounds, key availability, metadata exposure, and the deferred rotation/purge workflow.

Persisted verification accepts only an owned evidence ID, never caller-supplied recovery results, observations, rules, or actor identity. Decryption and Rust execution run outside database locks. Before committing, the service reauthorizes, locks invoice then case, validates audit history, and atomically records the attempt, explicit offline observation, captured evaluation, event, retry record, and case version/state. Technical failures remain distinct from invalid receipts. No approval or allocation is written.

Retries validate the stored result/evaluation references and event payload/header hashes, return the original attempt, and do not rerun Rust. Reports validate the complete event chain and read current balances/history in one repeatable-read snapshot. Global output conflicts reveal a boolean finding, not foreign invoice IDs or amounts. These checks detect inconsistent records; they do not provide signed replay or resistance to a database administrator rewriting the entire history.

Reports disclose recovered payment details to the authenticated merchant and require no decryption of the original bundle on read. Original receipt/raw-tx strings, OCKs, ciphertext, and keys are excluded, but the derived details remain sensitive. The report is an initial offline view, not an authorized reviewer export or replay packet. See [verification API and disclosure boundaries](verification.md).

Merchant decisions validate same-case verification ownership, reviewed case version, current credentials, captured policy, and fresh source-bound observation before credit. The default ASGI composition has no trusted chain source and rejects all simulated confirmation for new credit. Test/demo compositions alone inject a simulated observer and its source authority; there is no public trust field or runtime environment toggle. Stored successful observations are never reused as a substitute for refresh.

Resolution, evaluation, allocation, case update, audit event, and retry result commit atomically. A separately recorded refresh diagnostic can survive a blocked or failed decision. Semantic retries return an existing same-invoice resolution before stale/terminal rejection but still require current authorization and validate its history. Foreign allocation conflicts remain opaque. A recorded rejection is a merchant decision, not a change to cryptographic validity. See [resolution policy and disclosure boundaries](resolutions.md).

The optional [trusted chain adapter](chain.md) sends transaction IDs and block hashes to one operator-configured source. It never sends receipt/OCK/memo content. Configure HTTPS, or explicitly allow a private/loopback IP over HTTP; redirects and ambient proxy credentials are disabled. RPC credentials and full source responses are excluded from provenance and public errors. The source is a trusted provider assertion, not an independently verified consensus proof. Later observed loss of approved-output inclusion flags review and blocks additional credit without reversing history. Live compatibility and customer disclosure/consent remain pending.
